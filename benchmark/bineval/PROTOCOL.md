The instrument follows BINEVAL (arXiv:2606.27226; no public code — we author our

## 2. Two-tier scoring rules

**Tier 1 — normalized substring / alias match. NO LLM calls.**
- Base normalization is copied verbatim from `benchmark/longchat/score_eval.py`:
  NFKC -> lowercase -> fold unicode dashes to ASCII hyphen -> strip punctuation
  (`[^\w\s]`) -> collapse whitespace.
- Extensions over the base:
  - **Numeral table (1..20, and zero), bidirectional**: number words and digits
    are interchangeable. Both gold/alias and answer are canonicalized so
    "four" == "4"; e.g. gold "four days" matches answer "4 days".
  - **Alias list** (`tier1_aliases`): any alias matching is a pass. Aliases
    provide **unit-suffix tolerance** — a shorter alias ("12,000 yen") matches a
    prediction that drops a trailing unit phrase present in the gold
    ("12,000 yen per person").
- A candidate (gold first, then aliases in order) matches when its
  numeric-canonical normalized form is a substring of the numeric-canonical
  normalized, scrubbed answer.
- **Verdict routing in tier 1:**
  - substring/alias hit -> `pass` (tier 1).
  - empty answer OR whole answer is a no-answer/refusal marker
    ("not in context", "not mentioned", "unknown", "n/a", "none", ... — full set
    in `score_binary._NO_ANSWER_MARKERS`) -> `fail` (tier 1). A refusal is an
    unambiguous non-statement of the fact, not a judgment call.
  - any other non-matching concrete answer (possible paraphrase / wrong value)
    -> handed to tier 2.

**Tier 2 — binary LLM verdict, ONLY for tier-1 non-refusal misses.**
- Interface: a pluggable callable
  `judge_fn(question, gold_short, answer_text) -> bool | None`
  (`None` = still indeterminate). The judge sees only (question, gold,
  answer-fragment) — never the arm identity. Answer text is scrubbed before it
  reaches the judge.
- **This build ships `--tier2 none` (no API client wired).** Under `none`, every
  tier-1 non-refusal miss is written to `pending_tier2.json` (list of
  `{qid, question, gold_short, answer_fragment}`) and recorded as
  `indeterminate`; it is NOT scored.
- Frozen judge spec for when tier 2 is run (RESEARCH_PROGRAM sec.2 rule 2):
  Sonnet, temperature 0, 2 runs, majority vote; blinded to arm identity.
- Cross-check (rule 3): a 50-item subsample is re-judged by a non-Anthropic
  model (Codex GPT-5 CLI precedent). Disagreements go to manual review, never
  averaged.

**Alias policy (authoring rules for `tier1_aliases`):**
- Aliases exist to eliminate tier-1 FALSE NEGATIVES on correct answers only —
  never to broaden a gold into matching a wrong answer.
- Permitted: number-word/digit variants beyond the 0..20 table; comma/no-comma
  numerals; unit-suffix-stripped forms; surname-only for full names;
  well-known short forms of a proper noun that appears in the fact.
- Forbidden: aliases that would also match a DISTINCT valid fact in the same
  chat (e.g. never alias "12,000" so loosely it matches the 18,000-yen event);
  aliases derived from any model output; semantic paraphrases (those are tier 2).

## 3. Scrub rule (applied before matching AND before judging)

Remove CD scaffolding from answer text so it never affects a verdict:
- `[PN{mass}]` spans and any bare `[PN...` token — regex `\[PN[^\]]*\]?`.
- `<CONTEXT>` / `</CONTEXT>` markers — regex `</?context>` (case-insensitive).
- Collapse resulting whitespace.
Implemented in `score_binary.scrub`.

## 4. Answer <-> question mapping

- A `.txt` answer file in `A{n}: text` line format: the k-th SCORED question
  (after subset + exclusion filtering, in file order) maps to `A{k}`, identical
  to `score_eval.py` `enumerate(questions, 1)`.
- A `.json` answer file mapping `{qid: text}`: matched by qid (takes precedence
  over position when both are available).
- Directory `--answers`: one condition per `*.txt` (named by file stem);
  `.txt`-only by design so sidecar JSON is never mistaken for answers.
- `--subset {all|legacy|generated}` selects which questions are scored;
  `legacy` reproduces the original 16-answer alignment for the sec.2.6 sanity
  run.

## 5. Output

Per condition: `items` = list of `{qid, verdict: pass|fail|indeterminate, tier,
matched_alias?}`; `aggregate` = `{pass, fail, indeterminate, total,
pass_rate_tier1}` where `pass_rate_tier1 = pass / total` (indeterminate counts
as not-yet-passed -> a conservative tier-1 floor). Single-condition runs flatten
to top level; multi-condition runs nest under `conditions`. Indeterminate items
are additionally written to a sibling `pending_tier2.json`.

Windows: all file I/O is `encoding="utf-8"`; all console output is cp932-safe
(ASCII only).

## 7. Statistical decision machinery

- Power target (sec.2 rule 4): >= 300 paired binary checks per arm comparison
  (>= 390 for the parity-margin power below). Reuse `mcnemar_one_sided` and
  `bootstrap_ratio_ci` from
  `experiments/judges/v10_paired_2026_05_21/analyze_paired.py`
  (exact one-sided McNemar via `binomtest`; 10000-iter bootstrap, seed 47).
- Disagreements in the non-Anthropic cross-check go to manual review, never
  averaged.

## 8. Primary value axis and parity definitions (RESEARCH_PROGRAM sec.1.6)

Primary axis = **(a) token saving at parity accuracy** (non-inferiority).
Secondary/exploratory = (b) accuracy gain at parity tokens (the old 1.31× form).

Operational definitions (verbatim from sec.1.6):
- **Parity margin delta = 5pp**, pre-registered. Parity at budget B holds iff
  the one-sided 95% CI lower bound of (acc_arm - acc_full) >= -delta on paired
  items. **"No significant difference" is NOT parity** — non-inferiority
  requires the CI bound. Power: with ~390 paired binary checks, SE ~ 2.2pp ->
  delta=5pp is testable; delta=3pp would need ~900 checks.
- **Parity budget B\*(arm)** = deepest tested ratio at which parity holds
  (grid {2,4,6,10,20}x; reported at grid granularity).
- Headline claim form: "B\*(CD) = 6x vs B\*(best baseline) = 2x", plus physical
  corollaries (VRAM fit, latency, cost).
- **Mechanism claim (C3) in axis-(a) form:** w=alpha\* EXTENDS the parity region
  vs w=0 (B\* at least one grid step deeper), equivalently higher accuracy at the
  deepest common budget.
- **Program-wide metric convention** (sec.1.5): normalized recovery =
  (acc - floor) / (ceiling - floor), always reported next to raw pass rates;
  floor = no-context pass rate, ceiling = full-context pass rate.

## 9. Gate thresholds (verbatim from RESEARCH_PROGRAM.md sec.3)

Evaluated by Ryosuke only. Agents report numbers and CIs; they do not declare
pass/fail. If a number lands within +-2pp of a threshold, the default is FAIL
(sec.5 rule 3, pre-committed to avoid motivated reading).

- **G1 (after WO-2).** mass-order - random >= **+10pp** aggregate binary-pass
  rate at 6x budget, McNemar p<0.05, >=300 paired checks, random averaged over
  3 seeds.
  - Pass -> WO-4. Fail -> mass assignment is the blocker: open a redesign WO
    (semantic mass scoring); **all w-related work suspends** until a redesigned
    M passes G1.
- **G2 (after WO-4).** EITHER (parity form, sec.1.6): B\*(CD,w=0) >= 4x AND
  B\*(CD,w=0) > B\*(best baseline incl. LLMLingua-2); OR (superiority form):
  CD(w=0) - best baseline >= **+10pp** at ANY ratio in {4x, 6x, 10x}, p<0.05.
  Both forms pre-registered; either suffices.
  - Pass -> WO-6. Fail -> representation redesign; C3 deferred; the WildChat
    prevalence result (WO-5) still stands alone as a workload-characterization
    result.
- **G3 (after WO-6).** EITHER (parity form): B\*(CD,alpha\*) at least one grid
  step deeper than B\*(CD,w=0); OR (superiority form): (alpha\*) - (w=0) >=
  **+5pp** at 6x or 10x, AND gap(10x) >= gap(4x) (theory shape: guidance value
  grows with information density).
  - Pass -> mechanism confirmed where theory predicts; LME 2x2 closes out the
    old headline's attribution.
  - Fail -> mechanism claim retires to secondary position; C2 result becomes the
    primary contribution. This is a defined outcome, not a project failure.
- **G-strat (after WO-3, informational, non-blocking).** ratio(top-coherence
  tertile) > ratio(bottom tertile) on existing v10 verdicts -> supports the
  coherence-moderation hypothesis and calibrates C2/C3 expectations. Either
  outcome is publishable as an analysis.

## Budget definition (added 2026-07-07, pre-freeze)

- Compression ratio is ALWAYS defined against the RAW chat: B = raw_chat_tokens / ratio, tiktoken cl100k_base. The SAME B applies to every arm (truncation / summarization / LLMLingua-2 / CD). Restaurant raw = 172,773 tokens -> 6x budget B = 28,795.
- The CD's intrinsic serialization on restaurant data is 64,706 tokens (2.67x); ratios shallower than ~2.7x leave the CD un-evicted. Measured 2026-07-07: at B=28,795 the three policies keep 1,967-1,986 of 4,446 nodes with exact budget compliance.

### Rules added at iteration 2 (apply to all future scoring)

- **Judge model pinning.** When tier 2 runs, the exact judge model version (not
  just "Sonnet") MUST be recorded in the results metadata alongside temperature,
  run count, and vote rule. A run whose metadata does not pin the version is not
  comparable and must be re-run.
- **Cross-leak screen is mandatory for any future question additions.** Before a
  new or edited question is frozen, run the generated-included cross-leak
  acceptance check (adapt `_leak_check_tmp.py` / the empirical
  `results/pilot/leak_pairs.json` relationships): no included question's
  gold/alias (numeric-canonical normalized, word-boundary) may appear in any
  other included question's text. Zero violations is the gate.
- **Power statement.** With ~185 scored questions the paired design has a
  minimum detectable absolute difference (MDAD) of roughly **4-6 pp** for a
  paired comparison (arXiv:2510.08730). Per-category (per-session / per-type)
  claims are **out of scope** at this N — only aggregate paired comparisons are
  powered.
- **EpiCache comparability (arXiv:2509.17396).** When comparing against EpiCache
  or other budget-grid methods, budgets MUST be matched on the SAME raw-chat
  token basis (sec. "Budget definition" above); an EpiCache "budget" reported in
  KV-cache entries is not directly comparable to our token budget B and must be
  converted before any head-to-head number is quoted.
- **Novel-layer drop note.** The generated novel layer is dropped in v1.1 (see
  EXCLUSIONS.md "v1.1"): `novel_chat.json` sessions 1-18 duplicate the
  restaurant chat, so the true novel thread is only ~20K tokens and cannot carry
  the intended long-context load. The 16 legacy `novel_q*` records remain as a
  sanity anchor only. Layer 2 (below) replaces the novel layer as the
  second, third-party evaluation surface.

## Layer 2: PersonaMem-v2

A second, third-party evaluation surface, independent of the authored restaurant
questions, added to reduce single-dataset risk.

- **Source.** HuggingFace `bowen-upenn/PersonaMem-v2`, **CC-BY-4.0**, ungated.
  Wrapped by `personamem_loader.py` (import-safe; no I/O or model calls at
  import). Probe cache (a minimum subset) under
  `results/personamem_probe/`. Probe verified **2026-07-08** via
  `python -m benchmark.bineval.personamem_loader --probe`.
- **Tier: 128k.** Use the `chat_history_128k_link` histories
  (`total_tokens_in_chat_history_128k` == `metadata.final_token_count`); the 128k
  histories embed persona-irrelevant math/coding filler, which is the intended
  long-context stress. tiktoken `cl100k_base` for all token accounting.
- **History / question separation.** Chat histories live in
  `data/chat_history_128k/*.json` (`{metadata, chat_history:[{role,content}]}`);
  questions live one-per-row in `benchmark.csv` and reference a history by link.
  Many rows share one history (200 unique histories over 5000 rows). The history
  is what gets compressed; the MC question is asked against the (compressed)
  history. Never mix the two: compression sees history only, the scorer sees the
  question + options only.
- **Unmodified MC scoring.** Score each question as PersonaMem intends: a
  multiple-choice match of the model's pick against `correct_answer` vs the three
  `incorrect_answers` (JSON-encoded list). We do NOT re-derive golds, re-tier, or
  apply the restaurant tier-1/tier-2 substring machinery here — the MC label is
  authoritative.
- **Floor definition.** floor = **no-context MC accuracy** (answer the MC with
  the persona history withheld). This mirrors the restaurant floor: an item the
  model gets right without the history cannot separate context conditions.
- **Loader.** `personamem_loader.py`.
